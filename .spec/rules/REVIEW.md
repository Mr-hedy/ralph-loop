# Review 质量门规则

Review 是流程质量门，不是默认独立产物。它用于确认需求、方案、任务拆分、验证计划、实现结果和协作协议是否满足当前目标与稳定边界。

## 自动触发点

agent 在以下阶段必须执行 review，不需要等用户手动要求：

- 需求澄清完成、进入方案讨论或任务拆分前。
- 当前任务事实源完成任务拆分、进入执行前。
- 修改 `README.md`、`docs/`、`.spec/`、动作 workflow、任务事实源、脚本、模板或 generated project 合约后，最终回复前。
- 实施任务完成后、汇报完成前。

用户说“review 一下”“检查一下”“帮我看看有没有问题”等，也按本规则执行。

## 检查口径

按顺序检查：

- 目标一致性：产物是否解决当前目标，是否扩大范围。
- 事实源：是否引入第二套任务源、事实源、协议入口或陈旧路径。
- 追踪性：需求、方案、任务、验证和完成证据是否能互相追溯。
- 完整性：受众、非目标、成功标准、风险、验证和未覆盖范围是否缺失。
- 兼容性：是否误改项目模板、生成物合约、软链或只属于外部工具的检查边界。
- 可验证性：声明是否有真实验证路径，无法验证的范围是否明确。

需求类产物还要检查：

- `REQ-*`、`SC-*`、`BPF-*`、`FR-*`、`NFR-*`、`TC-*` 编号唯一且引用不断裂。
- P0/P1 需求有成功标准。
- 业务流程包含角色、触发条件、步骤、输入输出、异常分支和业务规则。
- 非功能需求和技术约束有来源依据，没有把 agent 偏好伪装成用户约束。

## 严重程度

- Critical：违反硬约束、破坏稳定合约、创建第二事实源，或遗漏会阻塞目标的核心覆盖。
- High：需求冲突、方案不可验证、安全风险或兼容边界不清。
- Medium：非阻塞追踪缺口、术语漂移、边界表达不足或验证不完整。
- Low：不影响执行的表达、格式或轻微重复。

## 输出规则

- 默认只在对话中输出高信号 findings，不创建 review 文档。
- 先列问题，按严重程度排序；没有问题时明确说明“未发现阻塞问题”，并列出剩余未验证范围。
- 每个问题说明位置、影响和建议修复方向。
- 发现需要持久化的问题时，直接更新权威事实源，或写入当前任务事实源的阻塞、待决策或后续任务。
- 不把风格偏好包装成缺陷，不用 review 替代实际验证。

只有用户明确要求审查报告、审计记录或异步交付材料时，才创建独立 review 报告，并同步 `docs/README.md`。

## 完成标准

- 结论清楚：通过、有条件通过或需要修改。
- 阻塞问题和非阻塞建议区分明确。
- 每个发现能追溯到目标、文档、代码、任务或验证缺口。
- 已说明未验证范围和剩余风险。
