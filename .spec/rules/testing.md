# 测试与验证规则

本规则指导 agent 如何设计验证策略，并把长期测试规范写入 `docs/architecture/testing.md`。验证计划回答“如何证明当前需求、方案或实现真的达标”；本轮具体验证动作写入当前任务事实源的对应任务。

## 进入条件

- 已有需求、方案、实施方案，或用户要求明确验证策略。
- 已知道主要行为、接口、文件结构或文档契约。

## 设计方法

先确认变更类型，再设计匹配的验证层级：

- 文档 / 协作规则：结构检查、链接检查、关键引用扫描、项目声明的完整检查命令。
- 脚本 / CLI：最小直接命令、错误路径、帮助输出、状态文件和退出码。
- 模板 / scaffold：fresh generated scaffold、force-refresh scaffold、软链和禁入文件检查。
- 任务执行 harness 相关：任务状态、run 目录、日志、退出原因、status/watch 行为。
- 高风险行为：增加同路径回归测试或人工复核步骤。

验证设计必须追踪到需求或契约：

- 每个重要需求、接口变化、事实源变化或模板合约至少有一个验证方式。
- 每条 P0/P1 `REQ-*` 至少有一个 `SC-*`，每条 `SC-*` 至少有一个验证方法。
- `SC-*` 的验证方法必须可执行或可复核，例如测试、演示、文档审查、脚本检查、监控数据或人工验收。
- Bug fix 或行为修复优先写能复现问题的检查，再让检查通过。
- 重构必须有变更前后都能运行的稳定检查；如果不能运行，说明原因。
- 文档和协作规则变更也需要验证入口，不能只靠“看起来对”。

验证设计时必须区分：

- 自动检查：可以重复运行的命令或测试。
- 人工检查：需要人观察的步骤和通过标准。
- 未覆盖范围：当前无法验证或超出本轮范围的内容。

## 执行循环

执行验证时按证据闭环：

1. 先运行最小直接检查，定位当前变更是否生效。
2. 再运行项目规定的完整检查；命令从 README、包管理配置、构建配置或既有验证文档确认。
3. 对生成物、软链、UI、文档索引或人工流程做必要观察。
4. 失败时先判断是实现、环境、测试设计还是需求不清，不要只修最近的报错。
5. 修复后重跑能证明该失败模式已消失的检查。

## 报告方法

验证结论必须基于真实命令、真实输出或实际观察。退出码 0 不是端到端成功的充分证据。

报告时说明：

- 命令：实际运行的命令。
- 结果：通过、失败、阻塞或未运行。
- 诊断：失败类型、失败测试名或关键输出。
- 未验证范围：没有覆盖什么，以及原因。

不要报告长日志；只保留能证明通过、失败或阻塞的关键行。

## 输出

长期测试规范按 `.spec/rules/templates/testing.md` 输出到：

```text
docs/architecture/testing.md
```

如果项目已有更具体的验证文档路径，优先沿用现有路径，并同步 README 文档索引。本轮执行命令、实际结果和未覆盖范围应记录到当前任务事实源的任务完成说明，不维护默认 `docs/testing.md`。

## 测试隔离规则

测试不得污染或破坏使用者环境。任何集成测试、smoke 测试、fixture 写入产生的副作用必须限定在临时目录或被测进程的子作用域内。

**强制要求**：

- **HOME 隔离**：测试若需要写入 `~/.claude/`、`~/.codex/`、`~/.gemini/` 等 provider 用户目录，必须先 `export HOME="$tmpdir/home"`，让 provider 文件落到临时 HOME 下，跑完即清。**禁止**直接写入真实用户 HOME。
- **PATH 隔离**：测试若需要修改 PATH（例如模拟某命令缺失），修改必须限定在被测子进程（`env PATH=... ralph run ...`），harness 自身 PATH 不得变更。harness 自己的 jq / git / bash 等工具必须始终可用，否则 harness 自身瘫痪后无法做断言。
- **配置文件隔离**：测试不得修改使用者的 `~/.gitconfig`、`~/.bashrc`、`~/.ssh/`、shell history 等配置；所有 git config 通过临时仓库的本地 config 设置。
- **网络隔离**：单元/集成测试默认不访问外网；需要真实 provider CLI 的 smoke 测试单独标识为人工触发。

**自检要求**：

- 集成测试结束时，至少做一项隔离自检（如 `ls ~/.claude/projects/ | wc -l` 跑测前后一致），把破坏类问题及早暴露。
- 失败时立即停止后续用例，避免雪崩污染。

## 测试基础设施单一来源

同类测试基础设施（mock 替身脚本、setup helper、fixture 文件）必须**单一来源**，不允许多个任务各自造一份。

**强制要求**：

- 第一个用到该基础设施的任务负责建立"骨架版"（最小可用 + 扩展点清晰），并明确标注"单一来源"。
- 后续任务在同一文件上**扩展**（加场景、加参数），不复制粘贴新建副本。
- 任务拆解时识别共享基础设施，把建立动作放在最早依赖它的任务，避免后续任务推倒重建。

违反上述规则会导致：测试基础设施分裂、行为不一致、维护时多处改动易遗漏。

## 完成标准

- 每个重要行为或文档契约都有验证方式。
- 自动检查和人工检查边界清楚。
- 未验证范围明确，不隐藏风险。
- 验证计划能被后续执行者直接运行或复核。
- 报告结论能从命令、观察和未覆盖范围追溯回来。
- 测试隔离自检通过，未污染使用者环境。
