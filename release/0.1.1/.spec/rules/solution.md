# 方案决策规则

本规则指导 agent 如何在存在真实取舍时和用户讨论方案决策。方案决策回答“有哪些可行方向、选哪个、代价是什么、哪些边界被锁定”，但不作为默认固定文档阶段，也不直接变成任务清单。

## 进入条件

- 已有用户明确目标，或已有 `docs/requirements.md` / `docs/requirements/<module>/`。
- 需求中的目标、非目标、受众和成功标准足够清楚。
- 如果需求仍有高影响缺口，先回到 `.spec/rules/requirements.md`。
- 存在多个真实可行方案，且选择会影响长期架构、稳定契约、迁移、安全、成本或用户流程。

## 讨论方法

先吸收 README、需求文档、现有 docs、代码结构和约束，再和用户讨论：

- 治理约束：`.spec/README.md`、README 文档地图、现有事实源和模板边界如何限制方案。
- 方案候选：至少比较一个推荐方案和一个可行备选，除非问题很小。
- 边界：哪些模块、文件、协议、脚本、模板或生成物会受影响。
- 数据和状态：主要输入、输出、状态源、持久化位置和权威事实源。
- 接口契约：是否涉及 CLI、文件格式、模板 payload、动作 workflow 入口、软链或外部系统边界。
- 兼容性：是否影响现有用户、旧文件、generated project、动作 workflow 或工具入口。
- 风险：实现风险、迁移风险、验证风险、安全风险和协作风险。
- 取舍：为什么选择当前方案，放弃方案的代价是什么。
- 决策：哪些选择已经锁定，后续不应重复争论。

方案决策阶段可以做研究，但研究必须服务于决策：

- 未知技术、外部参考、兼容行为或安全边界需要先查证，再写入方案。
- 研究结论使用“决策、理由、备选”三段表达，不保留长篇资料摘录。
- 外部参考只吸收可复用结构和约束，不成为运行依赖，也不照搬项目不需要的目录。

讨论时不要为了未来可能性增加抽象；复杂度必须由当前目标、当前证据和兼容需求支付。每个新增概念都要能追溯到需求、风险降低或稳定合约保护。

## 写法

- 优先描述行为、边界和取舍，不堆代码步骤。
- 对高风险变更先停在方案层，写清影响、迁移和验证计划。
- 记录被拒绝方案时写清拒绝原因，避免后续 agent 重复争论。
- 明确哪些选择是可逆的，哪些选择一旦落地会形成稳定契约。
- 不把 rejected designs 写进当前任务事实源。
- 不把运行日志或临时诊断当成方案证据。

## 质量门

方案决策进入实施方案前必须通过：

- 需求追踪：选定方案覆盖当前目标和非目标。
- 边界追踪：受影响文件、目录、协议或生成物明确。
- 事实源追踪：不会留下两个同等权威的任务源、规则源、状态源或模板源。
- 兼容追踪：对 generated project、软链、动作 workflow、脚本和既有入口的影响明确。
- 验证追踪：后续至少知道用哪些命令、脚本或人工检查证明方案成立。

## 输出

方案决策默认不创建独立 `docs/solution.md`。结论应沉淀到对应事实源：

- 业务取舍：写入相关 `docs/requirements.md` 或 `docs/requirements/<module>/`。
- 长期技术结构取舍：写入 `docs/architecture/**`。
- 本轮落地取舍：写入当前任务事实源的对应任务说明。

不维护独立 `docs/solution.md`。需要保留书面记录时，按 `.spec/rules/templates/solution.md` 的结构写成对应事实源中的“方案取舍”章节，并在 `docs/README.md` 中索引该章节位置。

## 完成标准

- 选定方案能追溯到需求目标。
- 受影响边界清楚。
- 关键备选方案和放弃原因已记录。
- 兼容性、风险和验证方向可被后续实施方案使用。
- 没有引入未付费的抽象、运行依赖或第二事实源。
