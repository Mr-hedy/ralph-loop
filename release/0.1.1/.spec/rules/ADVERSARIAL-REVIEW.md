# Adversarial Review 质量门规则

Adversarial review 是流程质量门，用于主动寻找方案、规格、任务和实现中的矛盾、遗漏、过度设计、事实源漂移和不可验证点。它不是否定方案，而是在高风险阶段降低遗漏和过度自信。

## 自动触发点

agent 在以下阶段必须执行 adversarial review：

- 存在真实方案取舍、准备固化方案前。
- 变更影响 `.spec/`、动作 workflow、任务事实源、脚本、模板、generated project 合约、权限、持久化边界或事实源路由时。
- Review 通过但仍存在高影响不确定性时。
- 方案看起来过度复杂、过度抽象，或同时保留新旧入口时。

用户说“挑刺”“反向审查”“挑战一下方案”“找风险”等，也按本规则执行。

## 审查问题

先站在失败场景里提问：

- 真实问题：方案是否解决用户目标，还是主要引入新体系。
- 最小性：有没有更小、更局部、更容易验证的做法。
- 事实源：是否留下新旧入口并存，导致 agent 或工具读错。
- 边界：是否混淆 `docs/`、`.spec/`、任务事实源、动作 workflow、checkpoint、postmortem、templates 和 generated output 的职责。
- 证据：是否把日志、临时诊断、退出码 0 或模型回复误当成端到端成功。
- 兼容性：是否把未来设计提前强加到当前项目。
- 迁移风险：旧文件、旧引用或旧任务源是否仍会误导 agent。
- 恢复路径：失败后是否能停下、回滚或交回明确控制面。

每个风险都要给出具体失败场景，不接受只有抽象担忧的结论。

## 风险分类

- 必须修复：硬边界违规、稳定合约破坏、第二事实源、隐藏的不可验证声明或高概率误导用户。
- 可观察风险：存在合理失败路径，但当前不阻塞；必须给出未来触发条件。
- 接受风险：风险真实存在，但当前取舍明确且代价可接受。

## 输出规则

- 默认只在对话中输出风险清单，不创建 adversarial review 文档。
- 先列必须修复的问题，再列可观察风险和接受风险。
- 每项包含失败场景、影响范围和建议处理。
- 如果建议更简单方案，必须说明它覆盖哪些目标，以及放弃哪些能力。
- 需要持久化时，更新权威事实源或当前任务事实源，不要创建并行事实源。

只有用户明确要求审查报告、审计记录或异步交付材料时，才创建独立报告，并同步 `docs/README.md`。

## 完成标准

- 高影响失败场景已覆盖。
- 必须修复和可后续观察区分明确。
- 建议不会引入更大的流程或抽象负担。
- 审查结果能转化为需求、方案、任务、验证、动作 workflow、脚本或模板中的具体修订。
