# TESTING 规则

本规则指导 agent 如何设计验证策略。项目长期测试规范按需写入 `docs/testing.md`；功能验证计划按需写入 `docs/features/<feature>/testing.md`。本轮具体验证动作写入当前任务事实源的对应任务。

## 进入条件

- 已有需求、方案、实施方案，或用户要求明确验证策略。
- 已知道主要行为、接口、文件结构或文档契约。

## 设计方法

先确认变更类型，再设计匹配的验证层级：

- 文档 / 协作规则：结构检查、链接检查、关键引用扫描、项目声明的完整检查命令。
- 脚本 / CLI：最小直接命令、错误路径、帮助输出、状态文件和退出码。
- 模板 / scaffold：fresh generated scaffold、force-refresh scaffold、软链和禁入文件检查。
- 任务执行 harness 相关：任务状态、run 目录、日志、退出原因、status/watch 行为。
- 高风险行为：增加同路径回归测试或人工复核步骤。

验证设计必须追踪到需求或契约：

- 每个重要需求、接口变化、事实源变化或模板合约至少有一个验证方式。
- 每条 P0/P1 `REQ-*` 至少有一个 `SC-*`，每条 `SC-*` 至少有一个验证方法。
- `SC-*` 的验证方法必须可执行或可复核，例如测试、演示、文档审查、脚本检查、监控数据或人工验收。
- Bug fix 或行为修复优先写能复现问题的检查，再让检查通过。
- 重构必须有变更前后都能运行的稳定检查；如果不能运行，说明原因。
- 文档和协作规则变更也需要验证入口，不能只靠“看起来对”。

验证设计时必须区分：

- 自动检查：可以重复运行的命令或测试。
- 人工检查：需要人观察的步骤和通过标准。
- 未覆盖范围：当前无法验证或超出本轮范围的内容。

## 执行循环

执行验证时按证据闭环：

1. 先运行最小直接检查，定位当前变更是否生效。
2. 再运行项目规定的完整检查；命令从 README、包管理配置、构建配置或既有验证文档确认。
3. 对生成物、软链、UI、文档索引或人工流程做必要观察。
4. 失败时先判断是实现、环境、测试设计还是需求不清，不要只修最近的报错。
5. 修复后重跑能证明该失败模式已消失的检查。

## 报告方法

验证结论必须基于真实命令、真实输出或实际观察。退出码 0 不是端到端成功的充分证据。

报告时说明：

- 命令：实际运行的命令。
- 结果：通过、失败、阻塞或未运行。
- 诊断：失败类型、失败测试名或关键输出。
- 未验证范围：没有覆盖什么，以及原因。

不要报告长日志；只保留能证明通过、失败或阻塞的关键行。

## 输出

长期测试规范按 `.spec/rules/templates/TESTING.md` 输出到：

```text
docs/testing.md
```

功能验证文档使用：

```text
docs/features/<feature>/testing.md
```

项目级和功能级文档都按需创建，不生成空白文件。本轮执行命令、实际结果和未覆盖范围应记录到当前任务事实源的任务完成说明。

旧项目的 `docs/architecture/testing.md` 在迁移完成前继续保持可读；新工作使用上述根级或 feature 路径。

## 完成标准

- 每个重要行为或文档契约都有验证方式。
- 自动检查和人工检查边界清楚。
- 未验证范围明确，不隐藏风险。
- 验证计划能被后续执行者直接运行或复核。
- 报告结论能从命令、观察和未覆盖范围追溯回来。
