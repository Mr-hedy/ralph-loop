# 需求澄清规则

本规则指导 agent 如何和用户澄清需求，并把功能需求写入 `docs/features/<feature>/requirements.md`。项目级聚合文档不是本规则的默认产物；只有存在跨功能稳定需求时才按需创建根级专题文档。需求阶段回答“要做什么”和“为什么要做”，不决定技术实现。

## 进入条件

- 用户提出新目标、功能、流程、迁移、修复方向或协作规则变更。
- 现有 README、docs、代码或任务源不足以支撑后续方案决策。
- 如果用户只要求执行一个低风险、边界明确的小改动，可以直接执行，但仍要在执行前明确成功标准。

## 澄清方法

先尽量从用户输入、README、现有 docs 和代码事实中吸收上下文。只有缺口会影响需求边界或成功标准时才提问。

需要引导用户澄清：

- 背景：为什么现在要做，触发问题或机会是什么。
- 目标：完成后用户、维护者或 agent 能做到什么。
- 非目标：本轮明确不做什么，哪些诱人的扩展先排除。
- 受众：谁使用、谁维护、谁评审。
- 使用场景：典型触发条件、输入、输出和用户路径。
- 成功标准：什么结果证明需求达成，最好可观察或可验证。
- 约束：时间、兼容性、安全、权限、运行环境、工具链、协作边界。
- 待澄清：当前无法确认但会影响需求判断的问题。

澄清输出先在对话中形成三段式确认，再写入文档：

- 当前理解：复述目标、范围、预期产物、受众和当前边界。
- 不确定点：列出 agent 识别到的歧义、矛盾、隐含需求或遗漏场景。
- 需要确认：只保留需要用户做业务决策、范围取舍或优先级判断的问题。

澄清时先做一次模糊度扫描：

- 范围：是否存在多个合理解释，且会改变功能边界、用户体验或任务拆解。
- 安全与隐私：是否涉及权限、敏感数据、外部服务、合规或数据离开机器。
- 受众与角色：是否有不同用户、维护者、reviewer 或 agent 角色。
- 行为路径：是否能写出典型输入、触发条件、输出和失败路径。
- 成功标准：是否可观察、可复核、与实现技术解耦。
- 非目标：是否足以阻止 agent 把诱人扩展塞进本轮。
- 术语：是否有同一概念多种叫法，或同一词指向多个概念。

提问时遵循：

- 只问会实质影响范围、架构、任务拆解、验证或安全边界的问题。
- 一次最多问 3 个高影响问题；超过的内容记录为待澄清或假设。
- 优先给用户 2 到 4 个具体选项，并说明每个选项的影响。
- 能从仓库事实、行业常规或项目边界做出低风险默认时，写入“假设”，不要打断用户。
- 发现需求本身与项目边界冲突时，先指出冲突，不要静默选择一个解释。

## 事实自查

澄清阶段不要把客观事实类问题推给用户。以下内容由 agent 自行查证，必要时优先使用官方文档、仓库源码或项目内证据：

- 技术名词、框架、库、协议、标准和开源项目的定义与适用边界。
- 版本差异、API 变化、兼容性、许可证和维护状态。
- 行业术语、合规标准和常见安全模型。
- 当前仓库已有入口、脚本、配置、文档和稳定合约。

只把需要用户裁决的问题留给用户，例如业务范围、优先级、验收口径、合规责任、预算、时间和组织偏好。

## 阶段化产物

Feature 需求应在同一 feature 目录内按需求分析链条组织；必要时可拆成多个阶段文档，但不能重新引入跨目录的需求散落：

| 阶段 | 目标 | 产物内容 |
|---|---|---|
| P1 澄清结论 | 消除歧义，锁定目标、角色、范围、非目标、约束和假设 | 澄清记录、已明确事项、仍需澄清事项 |
| P2 需求清单 | 将澄清结论整理成可编号、可排序、可审阅的需求 | `REQ-*`、模块、优先级、类型、来源 |
| P3 成功标准 | 为核心需求定义可验证验收口径 | `SC-*`、度量方式、目标值、验证方法 |
| P4 业务流程 | 抽取核心用户或业务路径、参与角色、异常分支和规则 | `BPF-*`、触发条件、步骤、输入输出、异常处理 |
| P5 详细规格 | 从需求和流程提炼功能、非功能和技术约束 | `FR-*`、`NFR-*`、`TC-*` |

不要求每次都生成所有阶段。低风险小改动可以只保留 P1-P3；涉及业务流程、复杂权限、外部接口、合规或多角色协作时，应补齐 P4-P5。

## 编号体系

需求文档使用稳定编号支持双向追踪：

- `REQ-001`：需求清单中的原子需求，项目内唯一。
- `SC-001-1`：绑定到 `REQ-001` 的第 1 条成功标准。
- `BPF-001`：业务或用户流程，必须引用相关 `REQ-*`。
- `FR-001`：功能需求，必须引用来源 `REQ-*`，有流程时同时引用 `BPF-*`。
- `NFR-PERF-001`、`NFR-SEC-001`、`NFR-REL-001`：非功能需求，类别前缀按性能、安全、可靠性等维度命名。
- `TC-STK-001`、`TC-INF-001`、`TC-INT-001`、`TC-REG-001`：技术约束，类别前缀按技术选型、基础设施、集成、合规等来源命名。

编号一旦进入被引用状态，不要复用；删除或合并时保留变更说明，避免后续文档引用断裂。

## 双向追踪

需求文档必须能支持以下链条：

```text
澄清结论 -> REQ -> SC -> BPF -> FR/NFR/TC
```

反向也必须成立：

- 每条 `REQ-*` 能说明来源：澄清轮次、用户确认、仓库事实或明确假设。
- 每条 `SC-*` 绑定到一个或多个 `REQ-*`，并有验证方法。
- 每个 `BPF-*` 引用相关 `REQ-*`，并说明角色、触发条件、输入、输出和异常路径。
- 每条 `FR-*` 引用来源 `REQ-*`；如果存在流程，引用相关 `BPF-*`。
- 每条 `NFR-*` 和 `TC-*` 说明来源依据，例如成功标准、业务规则、外部约束、用户指定或项目合约。
- 上游需求变化后，同步检查所有下游编号引用，不留下过期或矛盾内容。

## 写法

- 优先使用可验证描述，避免“更好”“更智能”这类模糊词。
- 对行为需求使用触发条件和预期结果，例如“当 X 时，系统应 Y”。
- 对核心需求使用稳定编号，例如 `REQ-001`，便于后续设计、计划、任务和 review 追踪。
- 对用户路径使用“场景 -> 验收”形式，确保后续可以设计测试。
- 成功标准必须技术无关，描述用户、维护者或 agent 可观察到的结果。
- 对不确定内容标记“待澄清”，不要让 agent 自行补全高影响假设。
- 对合理默认值标记“假设”，并说明该假设来自哪里。
- 不在需求文档里写具体实现步骤，除非用户已经明确指定。

## 质量门

写完需求后做一次自检：

- 没有实现方案泄漏到需求正文。
- 每个目标至少能追溯到一个需求或用户场景。
- 每个 `REQ-*` 都可测试或可人工复核。
- 成功标准没有依赖具体语言、框架、数据库或供应商。
- P0/P1 级核心需求至少有一条 `SC-*`。
- `FR-*`、`NFR-*` 和 `TC-*` 没有无来源条目。
- 所有高影响待澄清项都已提问、被明确延后，或写成有依据的假设。

## 输出

功能需求文档按 `.spec/rules/templates/REQUIREMENTS.md` 输出到 feature 目录，例如：

```text
docs/features/<feature>/requirements.md
```

一个 feature 目录代表一个可独立澄清、实施和验收的工作包。`solution.md`、`testing.md` 和 `final-task.md` 是按需创建的同级产物。

如果项目已有旧版 `docs/requirements/<module>/` 结构，在迁移完成前继续保持可读；新工作不再创建该结构。

`docs/README.md` 负责索引所有 feature 需求。拆分后必须保持 `REQ-*`、`SC-*`、`BPF-*` 编号在项目内唯一，并在 `docs/README.md` 中指向权威事实源。

## 完成标准

- 每个目标至少有一个成功标准。
- 非目标足够明确，能阻止范围蔓延。
- 关键需求有 `REQ-*` 稳定编号，后续产物可以引用。
- 双向追踪链能从核心需求走到成功标准、流程、功能需求、非功能需求和技术约束。
- 待澄清项不会阻塞当前可安全推进的下一步，或者已经要求用户决策。
- 文档能支持后续方案决策，不需要方案作者重新猜需求。
