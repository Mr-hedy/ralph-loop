# TROUBLESHOOTING 质量门规则

本规则指导 Agent 处理业务系统故障、线上异常、数据链路断流和跨服务行为不符合预期的排查任务。
它规定排查任务如何立项、收集证据、记录根因和声明未验证范围；不规定具体分析工具。

## 事实源与输出

- 具体业务排查文档写入 `docs/troubleshooting/<slug>.md`。
- Agent、工具链或协作流程的可复用失败模式继续写入 `docs/postmortems/`。
- 排查文档不是需求、架构、当前任务或 postmortem 的替代品。
- `docs/troubleshooting/` 只保存业务系统事实；不得写入 secrets、完整凭据或私人会话 transcript。

## 三层证据阶梯

### L1：业务领域定界

先说明问题涉及的业务实体、状态机、参与服务、消息或任务入口，以及期望状态和实际状态的差异。
如果已有领域图、架构说明或数据流文档，先引用它们并标出本次排查的范围。

### L2：调用、依赖和事件拓扑

在已定界范围内追踪 callers、callees、任务入口、消息生产/消费、事务提交后回调和状态写入边界。
可以使用静态分析、图谱、受控文本搜索或运行数据；工具不是证据本身，结论必须能回到具体节点、边界或观测。

不得把无边界的全局搜索作为唯一证据。`rg`、日志查询或图谱命中都必须说明扫描范围、筛选条件和局限。

### L3：局部源码和运行取证

最后回到最小范围的源码、测试、日志、指标、消息或数据库证据，定位具体判断分支、缺失调用、异常输入或配置差异。
对“不存在调用”“没有自动恢复”之类的否定结论，必须说明检查范围、方法和仍可能遗漏的边界。

## 排查报告要求

排查报告至少包含：

- 问题背景、影响范围和时间线；
- 期望链路与实际链路；
- 调查范围、假设和排除过程；
- 证据位置及证据类型；
- 根因，区分业务预期、代码逻辑、数据/配置和观测缺口；
- 临时止血、永久修复和防御机制；
- 已验证结果、未验证范围和后续人工决策。

异步边界必须显式标记。静态拓扑无法证明运行时消息投递、事务提交或调度执行时，应把结论标为待运行验证，而不是推断为已发生。

## 完成标准

- 报告可以从问题现象追溯到具体证据和根因；
- 业务排查和 Agent 失范复盘没有混写；
- 关键结论区分通过、失败、环境阻塞和未验证；
- 修复方案包含验证方法和长期防御机制；
- 如问题暴露了可复用的 Agent 或流程失败模式，再按 postmortem 规则沉淀。
