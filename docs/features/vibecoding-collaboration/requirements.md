# Vibecoding Collaboration 需求文档

- 状态：已确认
- 来源：2026-09-16、2026-09-28 用户澄清；2026-10-10 宿主/provider 边界确认；2026-10-30 将 mc-project 前台协作经验与升级后的 Ralph skill 回流；现有 `.spec/`、Ralph harness、handoff、checkpoint、postmortem 契约。
- 范围：Codex 作为 Main Agent 时，从需求澄清到 Ralph 前台/后台执行、动态任务调整、独立验收和长期协作记忆的整体工作方式。
- 变更条件：Main Agent 产品、Ralph 执行边界、事实源职责或 release 部署单元发生变化时重新评估。

## 摘要

本模块把 `ralph-loop` 从单一 CLI harness 扩展为面向 Codex Main Agent 的 vibecoding 协作脚手架。Main Agent 负责需求、方案、任务维护和独立复审；Ralph 通过 provider fresh oneshot 实施代码与测试。完整工作包默认采用前台协作，Main Agent 以关键执行证据校正任务；用户指定或执行与验证路径已有可靠依据时可采用后台托管。两种模式均以实际产物和行为作为验收依据。

Handoff、checkpoint、postmortem 分别治理 Main Agent 会话交接、已验收稳定锚点和可复用失败模式。它们可以互相引用，但不共享触发条件或状态机。

## 背景

- 长任务若全部在一个 Main Agent 会话中执行，工具输出、中间推理和反复修正会挤占上下文，增加决策漂移和幻觉风险。
- Ralph 已能通过 provider fresh oneshot 执行任务；实际协作表明，需求澄清与任务拆解不能提前证明实施路径正确，需要在执行中根据证据校正任务与验收方法。
- 现有 handoff 依赖用户或 Agent 主观判断何时切换会话，尚未接入 Codex 已提供的真实会话压缩事件作为客观评估入口。
- checkpoint、postmortem 和 handoff 已各自存在，但尚未在同一协作生命周期中明确职责和引用关系。

## 目标

- 让人类和 Codex Main Agent 以日常口语化沟通完成需求澄清和方案设计，在用户决定生成任务清单后拆解任务，并由 `.spec/` 作为持续生效的协作 harness 约束产物质量。
- 让 Main Agent 在用户授权后按明确模式托管 Ralph；新的功能工作包默认前台监督，后台执行须有用户选择或经过验证的实施与验收路径。
- 让完整工作包执行包含独立复审；仅启动、查询状态或明确暂缓复审时遵从较窄范围。任务勾选和运行终态不能替代验收。
- 让真实缺陷形成有证据、可验证的返工任务，在已有授权内继续实施与复审；目标、关键契约、权限或预算变化交给用户决定。
- 让 handoff 基于 Main Agent 会话的真实压缩状态触发评估，在用户授权下保存或切换到新会话。
- 让 checkpoint 保存已经验收的安全状态，让 postmortem 把重复或系统性失败转化为未来可执行的预防机制。
- 让上述能力随版本化 release 部署到新的使用者 workspace。

## 非目标

- 不把 `.spec/` 的需求、方案、任务拆解规则分别包装成必须显式调用的 Skill；`.spec/` 继续作为日常对话和文档产出的隐式协作 harness。
- 不让 Ralph 参与 Main Agent handoff 的触发判断；Ralph round、stall、provider session 和日志不属于 Main Agent 会话健康信号。
- 不把 Ralph 的 `result.json`、`exit-message.txt`、任务勾选或退出码当作需求完成证据。
- 不把 provider 完整对话、推理或日志回灌到 Main Agent；前台只按判断需要读取关键事件与产物，后台不持续消费执行过程。
- 不使用 Codex subagent 替代 Ralph 的核心任务执行职责。
- 不在首期依赖 MCP、外部项目管理系统、云端 agent 或不可版本化记忆完成核心流程。
- 不因 Ralph 正常结束自动创建 checkpoint、postmortem 或 handoff。
- 不把仅启动或状态查询扩展为完整执行与验收，也不把执行授权扩展为提交、推送、部署、归档或定时任务。
- 不允许 handoff 在没有用户授权时自动创建新 Main Agent 会话或转移修改权。

## 受众与角色

- **人类负责人**：确认目标和关键取舍，决定何时派发 Ralph，验收高影响结果并授权会话切换。
- **Codex Main Agent**：承担需求、方案、任务维护、模式选择、执行托管和独立复审；在授权内根据证据调整任务，维护协作记忆。
- **Ralph 执行引擎**：读取已确认任务，通过 provider fresh oneshot 修改 workspace；正常实现、自检与代码测试返工仍由其负责，不参与 Main Agent 会话治理。
- **Provider oneshot agent**：每轮按 Ralph 协议完成一个任务并退出，其内部会话不是 Main Agent 的事实源。
- **项目维护者**：维护 release、`.spec/`、动作 Skills、会话事件适配器、Ralph runtime 和验证门。

## 澄清记录

以下保留各阶段决策来源；轮次 2、4 中的默认后台、过程不可见及验收另行授权规则，已由轮次 5 更新。宿主/provider 分离、后台原生托管与通知边界继续有效。

### 轮次 1：外部 handoff Skill 评估

- 已确认：外部 `project-handoff` 只作为参考，不作为移植目标；本项目重新设计自身机制。
- 已确认：Codex Hook 是产品提供的生命周期扩展机制，支持 `PreCompact`、`PostCompact` 和 `SessionStart(source=compact)`；外部参考项目中依赖 `msvcrt` 的 Python handler 才是 Windows 定向实现，两者不能混同。
- 已确认：本项目不移植该 Windows handler；首期面向 macOS 自行实现最小会话事件适配器。

### 轮次 2：Main Agent 与 Ralph 边界

- 已确认：需求澄清和方案设计在 Codex Main Agent 主会话完成；用户决定生成任务清单后，由 Main Agent 在主会话拆解。
- 已确认：只有用户明确要求时，Main Agent 才后台运行 Ralph。
- 已确认：Ralph 具体执行过程对 Main Agent 不可见且不需要可见；正常验收不读取 provider 过程会话。
- 已确认：Main Agent 验收的是最终代码、测试、文档和 Git 状态，不是 Ralph 的运行报告。
- 已确认（2026-09-28）：用户决定何时生成任务清单及何时要求 Main Agent 验收；Ralph oneshot 可根据执行现场追加任务并记录依据，按验证结果勾选完成。Ralph 结束不自动启动整轮验收；验收发现的返工先与用户沟通，再追加任务。

### 轮次 3：协作记忆边界

- 已确认：handoff 只解决 Main Agent 长上下文和会话交接，不依赖 Ralph 进度。
- 已确认：checkpoint 是小功能完成并自测后形成的安全 Git 锚点。
- 已确认：postmortem 记录重复或系统性问题，并告知未来 Agent 在相似条件下如何处理。
- 已确认：`.spec/` 是人类与 Agent 日常协作的 harness，不是一个动作 Skill。

### 轮次 4：宿主原生后台托管（2026-10-10）

- 已确认：宿主是 Main Agent 所在的工作台，provider 是 Ralph 调用的 oneshot CLI；后台托管规则按宿主能力选择，不随 provider 切换。
- 已确认：用户要求 Ralph 执行已准备任务时默认后台派发，明确要求前台时按其要求执行。后台命令必须由宿主原生机制托管，用户可看到运行标识，Main Agent 保留可查询的命令句柄及对应 Ralph `run_id`；启动核对后主会话恢复可交互。
- 已确认：宿主能将完成结果交回 Main Agent 时，应读取终态并主动汇报；宿主不能主动恢复 Main Agent 时，启动时说明需人工查看。原生通知能力应保留，不以统一禁用通知适配能力较弱的宿主。
- 已确认：不为补齐通知能力擅自增加定时检查、Hook 唤醒补丁或外挂客户端；运行汇报不等于用户触发的产物验收。

### 轮次 5：默认前台、动态任务调整与独立复审（2026-10-30）

- 来源：[规划并执行阶段二后端任务](thread://01a18581-62ed-7a23-8f04-a72187b41810?hostId=local) 最后 12 轮的用户决定与升级后的 skill；用户要求将通用经验沉淀回 ralph-loop，并保留版本 `0.1.9`。
- 保留一个 `ralph` skill；入口维护共同规则，前台与后台流程分别在两份 references 中按需读取。技能正文用英文，项目文档与交流继续用中文。
- 默认前台；任务已拆完、改动较小或有测试不能单独证明适合后台。后台依据为用户明确选择，或执行路径已验证、范围固定、结果可可靠核对且无需持续独立判断。
- 主 Agent 持续观察关键证据，只在目标偏离、技术假设失效、验收假阳性、证据或预算风险等真实问题上介入；正常实现错误由 Ralph 自检处理。
- 调整前确认 Ralph、provider 与相关写入进程停止且锁释放，保留任务历史、部分成果、原始证据与累计预算；不靠重启重置用户限制。
- 完整执行授权涵盖当前范围内的任务调整、独立复审与必要返工；仅启动、状态查询、明确暂停或缩小范围优先，不反复索取同范围授权。
- Ralph `done` 仅证明执行终态。独立复审检查真实代码、测试条件、持久化/生成物及必要端到端行为；不因风格偏好追加验收门，不无依据重跑已验证版本。
- 后台不承诺持续监督；没有原生自动恢复能力时，复审等待用户返回，不擅自增设定时任务或外挂通知。

## 澄清结论

- 项目定位：Codex Main Agent 协作脚手架，Ralph 是独立执行引擎；前台/后台描述 Main Agent 的参与方式，不新增 CLI 模式或改变 provider。
- 主接口：Main Agent 向 Ralph 交付已确认任务；Ralph 向 workspace 交付最终工程产物。
- 任务边界：用户决定何时建立任务清单；oneshot 按协议追加现场任务；Main Agent 在已授权工作包内、确认写入停止后可据证据调整未完成任务或追加修复，已完成历史保留。
- 验收原则：真实产物和行为是完成证据；复用同版本有效证据，补齐风险匹配验证，运行结论只说明执行状态。
- 验收触发：完整工作包执行默认包含独立复审和必要返工；单独验收按用户范围，启动/状态查询等较窄请求不扩展，局部验收不等于整体通过。
- 上下文原则：前台只读取影响决策的关键事件与产物，后台启动核对后交还控制权；均不回灌完整 provider 会话，handoff 只观察 Main Agent 会话本身。
- 记忆原则：handoff 是可刷新接续状态，checkpoint 是稳定锚点，postmortem 是可复用失败知识；三者不互相替代。
- 授权原则：Ralph 派发、完整 handoff 和破坏性动作仍由用户或既有明确授权控制。

## 用户场景

### US-001：从想法到可执行任务

- 触发：用户在 Codex 主会话提出新的开发目标。
- 输入：用户目标、现有仓库事实和约束。
- 预期结果：Main Agent 按 `.spec/` 完成需求和方案，在用户要求时完成可验证任务拆解。
- 验收：文档和任务之间可追溯，且用户不需要逐个显式调用需求或方案 Skill。

### US-002：按模式执行并根据证据调整

- 触发：任务可执行，用户授权 Ralph 完成工作包。
- 输入：用户目标、任务源、workspace、provider 配置、现有证据与资源边界。
- 预期结果：默认前台，在关键节点只读核对；需要调整时先停止写入再修订任务并续跑。用户指定或路径可靠时后台托管，启动核对后交还控制权。
- 验收：模式与理由明确，不双写、不丢失进度或重置预算；完整日志不回灌，后台不承诺无法提供的主动通知。

### US-003：独立验收与范围内返工

- 触发：完整工作包实施完成，或用户单独提出验收诉求。
- 输入：需求、方案、成功标准、实际产物和同版本验证证据。
- 预期结果：Main Agent 判断目标是否满足，真实缺陷进入唯一任务源并在原授权内交回 Ralph 修复；缺少关键决定时停止盲目重试。
- 验收：执行结果与验收结果分别报告，阻塞问题未关闭不宣称完成；仅启动/状态请求不被扩展。

### US-004：长会话交接

- 触发：Main Agent 会话经历真实自动压缩，或出现已确认的上下文混淆。
- 输入：会话状态、当前项目事实和用户授权。
- 预期结果：系统在合适位置建议 handoff；获批后保存材料并由新会话核对后继续。
- 验收：不会因 Ralph 的内部进度误触发，也不会未经授权创建新会话。

### US-005：稳定点和失败知识沉淀

- 触发：相干功能通过验收，或任务过程中出现重复/系统性问题。
- 输入：最终仓库状态、验证证据和失败分析。
- 预期结果：分别创建 checkpoint 或 postmortem，并把预防规则放入实际执行载体。
- 验收：checkpoint 可定位可回滚；postmortem 能指导未来相似问题而不是只保存日志。

## 业务流程

### BPF-003：Main Agent 到 Ralph 再到验收

- 关联需求：REQ-033、REQ-034、REQ-035、REQ-036、REQ-037、REQ-038、REQ-039、REQ-045。
- 涉及角色：人类负责人、Codex Main Agent、Ralph、provider oneshot agent。
- 触发条件：用户提出开发目标。
- 主流程：需求与方案 → 用户决定建立任务 → 授权执行 → 明确模式并核对启动 → 前台关键证据观察 / 后台托管 → 必要时停止后调整任务并续跑 → 核对执行终态 → 按已有授权独立复审 → 真实缺陷返工与复审 → 报告验收结果。
- 异常分支：关键产品决定缺失不启动；明确暂停不自动续跑；仅启动/状态查询不扩展；控制协议不匹配保留现场；预算不足或关键决定缺失时停止；后台需持续介入时明确模式变更。
- 输入：用户目标、项目事实、需求、方案、任务源、workspace。
- 输出：对应 run_id 的执行结果，以及按授权完成的验收结论、未验证范围或待处理阻塞。
- 业务规则：Ralph 终态不等于需求完成；原授权持续有效，缩小范围或暂停优先；同一 checkout 单写入者，不跨重启清零用户限制。

### BPF-004：Main Agent Handoff

- 关联需求：REQ-040、REQ-041、REQ-044。
- 涉及角色：当前 Main Agent、用户、接手 Main Agent。
- 触发条件：发生真实会话压缩、已确认上下文混淆，或用户显式要求。
- 主流程：接收会话事件 → 要求评估 → 核对安全位置、明确后续和切换收益 → 提出建议 → 用户授权 → 保存 `handoff.md` → 创建/打开接手会话 → 接手方核对 → 转移修改权。
- 异常分支：用户选择继续则本次不交接；关键事实不清则先补齐；创建结果未知则查询而非重复创建；未授权则不新建会话。
- 输入：Main Agent 会话状态、项目事实、用户回应。
- 输出：继续当前会话、只保存材料、或已核对的接手会话。
- 业务规则：不以 Ralph 状态作为触发；运行状态不是项目事实。

### BPF-005：Checkpoint

- 关联需求：REQ-042、REQ-044。
- 涉及角色：人类负责人、Codex Main Agent。
- 触发条件：相干工作单元已完成并通过相应验证，且当前状态值得保留为安全锚点。
- 主流程：确认范围和工作树 → 执行 postmortem sweep → 记录验证和风险 → 只暂存相干改动 → 创建 checkpoint note 和 commit → 回读确认。
- 异常分支：存在无法分离的无关改动、状态未验证或仍是实验时不创建。
- 输入：已验收 workspace、验证证据、postmortem 状态。
- 输出：唯一 commit 和 checkpoint note。
- 业务规则：普通执行 commit 不自动成为 checkpoint；checkpoint 表示已审查稳定点。

### BPF-006：Postmortem

- 关联需求：REQ-043、REQ-044。
- 涉及角色：Codex Main Agent、项目维护者、未来 Agent。
- 触发条件：重复错误、回归、系统性边界问题或预防机制失效。
- 主流程：检索已有条目 → 分析现象、根因、修复和适用条件 → 新增或更新条目 → 定义 prevention check → 把未来行为提炼到正确载体。
- 异常分支：一次性低价值错误不记录；已有条目覆盖时更新或引用；缺少根因时标记待补而不伪造。
- 输入：可复核失败证据、修复结果和影响范围。
- 输出：可检索失败模式及至少一个具体预防方向。
- 业务规则：postmortem 不是日志，也不是需求或当前任务事实源。

## 功能需求

### FR-009：Ralph 模式选择与托管

- 来源需求：REQ-035、REQ-036、REQ-039、REQ-045。
- 关联流程：BPF-003。
- 用户故事：作为 Main Agent，我希望按执行与验证的不确定性选择参与方式，以便及时校正任务，同时控制上下文噪声。
- 输入：已确认 workspace、任务源、provider 配置、用户授权与限制。
- 输出：明确模式、已核对的宿主句柄和 run_id、关键发现与下一核对点；后台说明完成通知或人工返回方式。
- 业务规则：默认前台，用户模式优先；后台需要用户选择或可靠路径依据。运行期间 Main Agent 只读，停止全部写入后才调整，恢复先核对原 run 与部分成果。操作唯一入口为 `.agents/skills/ralph/SKILL.md`，两种模式不增加 CLI 参数。

### FR-010：独立复审与返工

- 来源需求：REQ-037、REQ-038。
- 关联流程：BPF-003。
- 用户故事：作为人类负责人，我希望完整执行包含独立复审与必要修复，以免只凭 Ralph 自报完成交付。
- 输入：需求、方案、任务、派发前基线、最终产物与同版本验证证据。
- 输出：`accepted`、`accepted-with-residual-risk`、`rework-required` 或 `blocked`，以及证据和未验证范围。
- 业务规则：完整授权内继续复审返工，较窄请求优先；复用有效证据并补齐必要验证。任务修订保留历史与预算，实施交回 Ralph；范围、关键契约、权限或费用变更交给用户，不以风格偏好扩大验收。

### FR-011：会话健康跟踪与 Handoff

- 来源需求：REQ-040、REQ-041。
- 关联流程：BPF-004。
- 用户故事：作为长会话使用者，我希望系统根据真实压缩事件要求评估 handoff，以便在上下文退化前切换且不被机械打扰。
- 输入：Codex Main Agent 生命周期事件、当前交接状态、用户回应。
- 输出：无需提醒、延后、交接建议、已保存或已接手状态。
- 业务规则：事件采集与业务判断分离；无用户授权不创建新会话。

### FR-012：稳定锚点

- 来源需求：REQ-042。
- 关联流程：BPF-005。
- 用户故事：作为项目维护者，我希望在已验收安全点创建可追溯 checkpoint，以便后续工作失败时可明确回退。
- 输入：相干改动、验证结果、工作树、postmortem sweep。
- 输出：checkpoint note、commit 和剩余风险。
- 业务规则：不混入无关改动，不用未验证草稿冒充稳定点。

### FR-013：失败知识沉淀

- 来源需求：REQ-043。
- 关联流程：BPF-006。
- 用户故事：作为未来 Agent，我希望在相似失败条件下能找到适用条目和 prevention check，以便不重复同类错误。
- 输入：失败证据、根因、修复和适用范围。
- 输出：postmortem 条目及规则/检查提炼位置。
- 业务规则：一次性低价值错误不创建条目；只记录脱敏证据。

## 假设

- Main Agent 与 Ralph 默认操作同一个本地 Git workspace，但任一时刻只有一个业务写入者。
- Ralph 的后台托管使用 Main Agent 宿主的原生机制；能力需要在当前宿主核对，不从 provider 名称推断。缺少原生托管时由用户选择前台或人工执行，缺少主动通知时人工查看终态。
- Handoff 首期使用 Codex 本地生命周期事件作为客观信号；事件不可用或项目 Hook 未获信任时退化为显式用户调用和人工自检。
- Ralph 的 result/status 用于核对执行身份与终态；最终产物及风险匹配的验证证据用于独立验收，两者不能互相代替。

## 边缘情况

- Ralph 报告 `done`，但代码没有满足成功标准：必须进入 `rework-required`。
- Ralph 失败但留下部分有价值改动：Main Agent 先确认进程已停止，再审查工作树并决定保留、返工或回退。
- 用户在 Ralph 运行中要求修改任务或产物：确认原 run 及相关写入已停止后再修改；不自动创建或切换 worktree。
- Main Agent 在 Ralph 运行期间发生 handoff：接手材料必须记录运行控制句柄和写入权归属，但不能把 Ralph 内部过程复制进 handoff。
- 自动压缩发生在尚未安全收拢的位置：记录待评估状态，继续到最近安全点再建议，不强制中断。
- Checkpoint 前发现重复失败：先完成 postmortem sweep 和必要沉淀，再创建稳定锚点。

## 待澄清

- Handoff 是否需要在每次压缩评估之外增加静默期或更细的提醒频率控制，应通过真实长会话试验校准；首期不移植外部参考实现的计数阈值。
